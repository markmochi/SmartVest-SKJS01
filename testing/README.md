# SmartVest testing

`system/` contains integrated firmware, transport and sensor checks, with shared host adapters. `main/` contains Main, camera and browser checks and their fixtures. `sensing/` contains the real Sensing driver, detector and board integration suite. Production firmware remains under `Main_and_Cameras/`, `Sensing/` and `Nano/`.

From the project root, run `python tools/run_checks.py --host --browser --output PATH_TO_RESULTS` with the dependencies described in `docs/DEVELOPMENT.md`. Every test entry also runs directly at its new path. Use `--list` to inspect the complete selection, or `--only` for specific entries. Python and Node checks run in separate processes, normally limited to 180 seconds each; the full pin-profile matrix has 900 seconds. `--timeout SECONDS` overrides that budget without reducing the test cases. Use `python testing/sensing/run_tests.py --main Main_and_Cameras/SmartVest_SJKS01_Main --arduinojson PATH_TO_ARDUINOJSON_SRC` for the full Sensing suite.

The camera writer/window suite runs with `--host`. Its external playback phase reports a skip when FFmpeg or ffprobe is absent; `--media` requires both. The optional `--sockets` suite uses actual POSIX sockets and is separate from the portable socket model. Hardware diagnostic actions in the administrator dashboard remain part of the product, protected by their existing authorization and configuration gates.

Set `SJKS_TEST_OUTPUT` to collect generated logs and browser images outside source. Its default is `testing/results/`; this directory is excluded from the source manifest. Browser images and text results use separate suite folders. Temporary compiler fixtures use the operating system temporary directory.

Host and simulated-browser checks do not exercise physical wiring, radios, power, sensors, real recipients or SD media. Live acceptance instructions are in `docs/VERIFICATION.md`.

The dashboard checks in `main/` include `test_dashboard_redesign.cjs` (19 routes, two appearances, six widths and visual outputs), `test_dashboard_loading.cjs` (held/missing resources, late results and read cancellation), and `test_dashboard_soak.cjs` (eight virtual hours of session/lifecycle checkpoints). The scene test verifies pose geometry and theme changes without extra GPU allocations. These run through `--browser` as well as directly.

`main/test_dashboard_startup_recovery.cjs` interrupts runtime, entry, shared dependency and page downloads for both roles. It also injects initial session/settings 503 and truncated JSON responses, visits every route, and verifies embedded styling, automatic recovery, reuse of successful modules, one document/runtime/session and no repeated writes. These failures are simulated locally; physical network behavior remains a separate acceptance check.

`main/test_camera_status_recovery.cjs` holds the first camera summary, verifies that both camera cards already exist, then fails event-history responses while current status keeps updating. It checks bounded automatic history recovery without reloads or writes. The production diagnostic handler fixture exercises separate summary and event views, including their temporary allocation measurements.

HTTP memory regressions include actual installed ESP32 String methods (`system/test_http_string_memory.py`) and retained String capacity in production transport tests. `main/test_status_response_memory.py` executes the full administrator status handler and real service JSON writers using a 32-bit host target (`-m32`, or the runner's Windows Zig target); a native GCC installation needs 32-bit libraries. This matches ESP32's pointer size and ArduinoJson pool profile, without claiming an actual-device memory measurement. `main/test_polling_errors.cjs` checks first-read, HTTP and rendering failures, escaped diagnostic text and recovery.

## Responsiveness regressions

`main/test_ride_backpressure.cjs` executes the recorder and diagnostic reader with controlled time, failing IMU endpoints and repeating trace cursors. `main/test_wifi_workload.py` executes Main's AP policy, internal-heap guards and the actual camera request helper under transient and invalid responses. `main/test_dashboard_navigation.cjs` exercises delivered modules across repeated page changes, held reads, Back/Forward and active-recording departure/recovery. The shared Sensing response is checked without a duplicate pose request. These fixtures verify bounded behavior; they do not establish actual radio recovery or a hardware root cause.

`main/test_web_routes.py` executes production lookup against all 51 generated routes, including valid and malformed retry aliases, exact asset version, payload/MIME/header handling, GET/HEAD, wrong hosts, unsupported methods and unknown routes. `main/test_web_assets.py` independently decompresses and hashes every embedded payload against its source and manifest, including the exact hashes authorizing embedded styles and startup code in CSP.

`main/test_dashboard_responsiveness.cjs` checks two delayed-API clients, scoped rider data, a held pose yielding to foreground refresh, prompt initial-503 recovery, unchanged write counts and real negative readiness. API queue tests additionally check immediate queued cancellation, GET preemption and exactly-once writes. Production transport tests cover TCP_NODELAY, one-packet small replies and partial writes across the header/body boundary. The 32-bit status fixture checks all rider views with a full twenty-job history and the Ride Test view against the full module values. These are software models, not physical radio measurements.

The dashboard lifecycle suites `test_all_pages_recovery.cjs` and `test_page_work_lifecycle.cjs` exercise all 19 routes with two signed-in sessions, held initial replies, transient 503 recovery, cancellation of a stalled diagnostic export, a stalled camera-history read, and navigation during and after a contact save. They execute delivered assets against local API fixtures; their timings are not radio measurements.

The account/reset checks are `test_accounts_reset.py` (production route handlers), `test_admin_account_reset.cjs` (delivered UI, separate sessions and live form refresh), plus the extended security, storage and emergency suites. They cover role isolation, credential persistence, current-password/CSRF rejection, active-work refusal, storage-failure/reboot completion, preservation of administrator access, and crash replay suppression after clearing displayed records.

The rider onboarding browser check covers first use, required contacts, failure/retry, calibration skip, reload, contact removal, reset, responsive widths and reduced motion. The visibility recovery check exercises the production poller across simulated hidden/foreground events and elapsed time, including genuine disconnection and recovery. These are browser fixtures, not a physical RF measurement.
