# Camera security and recovery

Install this Main firmware and **both** matching camera roles together. Product identity remains 1.0. The camera authentication protocol is now 2; old bearer-based firmware has no fallback. Sensing, Nano, detector thresholds, saved calibration, GPIOs, private key values, wire records, Main incident journal and partition table are preserved.

## Recording and crash footage

Each camera still targets VGA MJPEG, eight frames per second and one-minute segments. It retains up to thirty ordinary clips. Count cleanup and low-space cleanup both reclaim the oldest eligible ordinary footage. Low-space cleanup may shorten available prehistory; it cannot manufacture missing five-minute coverage. Before a frame exhausts the reserve, ordinary clips are reclaimed again. Protected clips, unknown files, corrupt metadata and recovery originals are never disposable FIFO entries. If these fill the card, recording reports failure rather than deleting them or formatting the card.

Crash requests still cover five minutes before and after the original trigger, with the measured transport allowance. Receipt means intent was saved. Full protection requires finalized clips, saved pins, the matching recording session, complete timing/gap coverage, authenticated clip/event metadata and a fresh incremental AVI verification. The verifier checks every canonical header byte, all frame-index entries, exact sizes, JPEG boundaries, padding and the SHA-256 payload. It reads payloads in at most 8 KiB slices between scheduled captures; starting a file loads its bounded index (at most 16 KiB). It does not decode every JPEG on the ESP32 or reconstruct the physical crash.

Main no longer fails a camera merely because seven minutes passed. The administrator incident view marks overdue responses while delivery continues. Unreceived requests take priority; requests already received rotate independently. A late protected response may upgrade a known failed incident; protected cannot be downgraded by an older received/failed response. Original trigger age is retained while Main stays running. After Main restarts, an unknown original age stays unknown; replaying an existing camera intent does not reset its trigger.

The existing bounded journal remains four incidents with three active automatic/type-5 slots and one reserved ordinary-crash slot, plus sixteen retired identities. There is no infinite backlog. If unresolved entries occupy capacity, existing readiness/backpressure applies instead of silently expiring evidence. A retired identity cannot recreate its removed full record from a late ACK.

## Interrupted recordings

During recording, the AVI data is flushed before a keyed checkpoint is appended and flushed, approximately once per second between captures. A final checkpoint includes the intended public video name before finalization. Checkpoints bind the camera role, stable clip identity, recording session, actual frame timestamps/count/gap, committed byte boundary and payload digest. Torn or altered records are rejected. File flush in the installed ESP32 core calls both `fflush` and `fsync`; filesystem/card/controller and supply behavior still require physical power-cut tests.

Recovery copies only the latest valid committed frames into a newly indexed AVI and verifies that output. It publishes a deterministic `_PROTECTED_INTERRUPTION.avi` replacement, saves keyed metadata, reserves the original identity, and then archives the immutable original as `.raw` under `/system/recovery`. The authenticated checkpoint is retained there too. A failed write, failed rename, restart or conflicting output preserves the original. Recovery never overwrites an unrelated public video. Recovering files requires enough spare capacity for a copy plus the recording reserve; otherwise recording continues and recovery waits.

Legacy interrupted `.part` files without checkpoints can salvage structurally complete JPEG frames. Their original timing/integrity cannot be established retrospectively: metadata explicitly marks them legacy/recovered, their timing is illustrative, and they cannot satisfy a full crash window. New checkpointed recovery is also partial evidence, never a substitute for the lost post-event window. Invalid/key-mismatched fragments stay retained for inspection.

Preserve `/system`, including clip/event metadata, identity/pin markers and recovery originals, together with `/clips`. Export/review protected evidence before freeing space manually. Do not erase metadata to make the recorder appear healthy.

## Authenticated communication

The long-term camera key is never sent as an HTTP bearer token. A keyed client hello obtains a random Main challenge with a server proof. The camera proves possession on the first signed request before replacing an active session. A pending handshake cannot evict a working session. Pending handshakes expire after fifteen seconds; cameras renew sessions after thirty minutes or before sequence overflow.

HMAC-SHA256 binds role, both nonces, increasing sequence, method, exact route and body; replies also bind the status. Main rejects repeated/older sequences, wrong bodies/routes/roles and stale sessions. Cameras reject unsigned or altered responses before applying commands, clocks, log acknowledgements or ACK outcomes. Responses and request bodies are bounded to 4 KiB. Existing Wi-Fi retry pacing remains separate from local recording.

This provides authentication, integrity and replay defense over the existing local HTTP connection. It does **not** add TLS, conceal traffic, encrypt the SD card, prevent radio jamming/physical removal, or protect against someone who possesses the firmware's private key. Main still trusts an authenticated camera's verified outcome; video is not uploaded to Main. Existing web-server parsing/resource limits remain separate from these camera checks.

Keys intentionally survive NVS erase; erase is not revocation. If a key is exposed, provision a fresh independent 32-byte random key for that role in the canonical private pairing header, synchronize copies, rebuild Main and the affected camera, and install them together. Preserve the old key/header privately only if it is needed to verify older keyed evidence. Old-key metadata is retained but cannot be certified with a new key. Never put keys in logs, reports, browser storage or source-control publications.

The read-only `Main_and_Cameras/tools/check_evidence.py CARD_ROOT` now verifies keyed event/clip records, canonical AVI structure and payload integrity. Its default key source is the private canonical pairing header; `--pairing-header` selects a matching older header without putting keys on the command line. `--decode` additionally invokes installed ffprobe/ffmpeg. Legacy/unsealed or incomplete incidents do not pass full-window certification. The auditor never unlocks or rewrites files.

## Availability and resource bounds

Command handling uses a bounded recent catalog (forty finalized clips) and at most sixteen overlapping clips per event. It no longer scans every SD metadata file while accepting a command. A delayed request older than the RAM catalog searches retained metadata one entry per idle call, pinning only the matching window; older already-protected footage can still be reconciled. Startup enumerates the card with bounded RAM; startup time still grows with card contents. Each idle call selects one primary maintenance step: ready evidence verification first, delayed catalog lookup next, fragment recovery last. A separate bounded recording library step can follow, so browsing cannot be starved by a long verification. Recovery scans one entry/checkpoint or copies one 8 KiB slice per step. The recording library processes at most one metadata entry per idle call and rejects deletion or download during protection or recovery; a file-result retry alternates with incident command polling. Old files remain on disk; the RAM catalog does not grow with all locked evidence.

Malformed finalized metadata is quarantined without deleting its video. A damaged existing protection marker keeps footage protected and raises an inspection warning instead of stopping all future recording. A new recording session is greater than the retained NVS counter and valid card clip/checkpoint sessions, including after ordinary NVS loss/card migration. An exhausted/unwritable counter fails safely. Filename collisions and recovered identity markers prevent replacement.

Initialization/capture/stalled-image failures retry camera initialization with one-to-thirty-second backoff. Recovery breaks recording continuity and starts a new session; old incidents retain partial evidence. Operator Serial `s` is a separate deliberate stop and never automatically resumes. Power off after STOPPED before removing the card.

Media indexes and scratch buffers use 64 KiB of bounded, lazily allocated camera PSRAM. Allocation failure cannot claim readiness. Main keeps PSRAM disabled and the existing partition layout. Dashboard delivery now shares one layout across all nineteen routes; boot selects the appropriate navigation before binding, while session/API role enforcement remains authoritative. Pinned build-only minification/gzip tools reduce stored assets without changing the approved design.

## Verification and hardware acceptance

Software checks execute the production auth/session/HTTP functions, incident coordinator, AVI writer/verifier, checkpoint repair, recovery commit, metadata/catalog policy and camera retry block. Fault cases include every header byte, torn/corrupt checkpoints, interrupted repairs, rename/write failures, wrong role/identity, replay, conflicting files, low-space reclamation, malformed metadata, legacy fragments and many locked clips. Pillow independently decodes generated VGA frames. Existing browser regressions cover both consoles and responsive/freshness behavior. Retained outcomes and role-specific build hashes are in [Verification](VERIFICATION.md).

No hardware was flashed, SD card accessed or SMS sent by these checks. Physical acceptance still needs both actual cameras/cards/supplies: long recording and playback, camera-only lock diagnostics after enough prehistory, Wi-Fi outages before/after receipt, multiple requests, controlled interruption during capture/finalization/repair, nearly full storage and sensor/card recovery. Measure actual frame gaps, heap, PSRAM and supply/RF behavior. Software bounds do not guarantee a particular SD I/O latency or survival of damaged hardware/filesystems.

## Recording library

Camera firmware 1.0.6 advertises library support in its authenticated heartbeat. Main retains one bounded request and result per camera. The camera owns SD access and supplies at most five entries per page. Paging uses recording session, start time and stable clip identity rather than an offset that shifts when new clips arrive. Main does not download video data or retain the entire SD catalog. Read requests can share a signed command reply with incident protection. When all incident and alert work is terminal, old failed incident retries are deferred during clip management or an active download. Fresh unfinished incidents retain priority. The dashboard waits for an existing camera job before submitting another operation; result polling has a 125 second overall deadline and never replays an accepted deletion.

Library requests use the existing signed camera command channel; result submissions are signed and bound to the camera role, stream and request ID. Main checks the signed-in role, origin, CSRF token, fresh camera status and explicit deletion confirmation. Requests are not persisted across reboot. A repeated ID cannot repeat the camera deletion, and a changed stream or recording session invalidates work. Main withholds deletion while incident protection or alerts are pending; the camera also stops on active evidence or recovery work.

Deletion visits existing finalized metadata one entry at a time. It excludes the active recording and recordings started after the request began. Video removal happens before supporting metadata cleanup, so partial cleanup cannot unprotect a surviving AVI. Normal-only deletion skips all protected recordings. All-clips deletion includes protected saved videos, but preserves recovery originals and unrecognized or damaged records. A discrepancy or file-operation failure is reported rather than silently called complete. Protection timestamps are recorded for newly pinned clips and newly committed recovered copies only when a clock is available; absence is represented as unknown.


## Single download lease

Downloading checks unfinished protection on the selected camera, separately from the stricter incident-data deletion guard. Pending SMS and unfinished protection on the other camera do not block starting or renewing a saved-clip download. A new incident on the selected camera still cancels the transfer. Camera-local active protection, verification and recovery still require waiting; normal crash monitoring itself is not a download lock. Main must have healthy incident/settings storage, and a data reset must not be pending. Delete operations retain their existing all-incident/all-alert checks.

Main authorizes file operation 5 with a fresh 128-bit capability and reserves one download across both cameras and account roles. Operation 6 requests cancellation by the owner session or an administrator. Job polling exposes the temporary camera URL only to its owner. Camera addresses come from authenticated heartbeat connections, not a submitted URL. All catalog/deletion requests are excluded while the lease is active.

The existing signed command channel carries a short camera lease. The camera subtracts the measured request round trip and a safety margin; its permission ends before Main reuses the global slot. Main renewal requires matching camera stream, job identity and a live owner session. After Main boots, a twelve-second download fence lets every prior camera lease expire before admitting a new transfer; dashboard access is unaffected. Cancellation does not immediately release the global slot: a terminal camera report or expiry does. The overall transfer limit is fifteen minutes. No lease or recording pause flag is persisted to NVS or SD.

Only the recorder task opens the selected read-only file and performs SD reads. Metadata identity, session, start and exact file size are checked, with the existing seal validation for schema 2 records. The current segment is finalized before pausing. The temporary socket server accepts one whole-file GET with the capability, enforces a 2048-byte header limit and a three-second header deadline, and sends through a lazily allocated 4096-byte buffer using nonblocking writes. It does not buffer a video on Main or in dashboard JavaScript. A five-second stalled-write limit and a thirty-second first-client limit supplement the lease and overall deadline. Range requests require a new whole-file attempt and are not silently resumed. Transfer completion means payload submission to TCP, not confirmation of phone storage.

The listener closes after its first accepted peer and the file, connection and buffer are released on completion, cancellation, errors or lost permission. Recording resumes if it was active before the download. Recovery handles storage or restart failures. A LOCK aborts the transfer before ordinary evidence handling. Existing coverage verification continues to report actual gaps, including an intentional download pause. Downloads never unprotect or explicitly delete the source clip; ordinary normal retention resumes afterward.

The browser uses a sandboxed hidden frame with download permission, no referrer and no scripts. The dashboard policy permits frames only on HTTP port 8081 while keeping script and API sources restricted. The camera serves an attachment with a fixed length and no-store/nosniff headers; it serves no browsing, upload or arbitrary filesystem endpoint. The capability is not a permanent camera password. Test direct station communication, native browser saving and Wi-Fi/heap behavior on the actual vest.

## Protection labels and timestamps

New incident recordings use `_PROTECTED_INCIDENT.avi`; this includes crash alerts and explicit protection tests. Recovered interrupted recordings use `_PROTECTED_INTERRUPTION.avi`. Both are excluded from normal automatic deletion. The lists in both dashboards report the reason from verified metadata; legacy records without a reliable reason remain explicitly unknown. Verified older `_LOCKED.avi` names are changed to the appropriate suffix during the normal card scan, without rewriting video or changing the stable metadata identity. Rename conflicts retain both files and raise an inspection warning. All three protected suffixes remain readable, including during interrupted migration; deletion and downloads use the same lookup.

A valid clock received during recording is captured in the next checkpoint. Recovery retains that saved recording time and records a separate recovery time if a valid clock is available when a new recovered copy is committed. A restart cannot reconstruct a timestamp that was never saved. Missing recording or protection times remain explicitly unavailable in the dashboard; recovery or migration time is not substituted for original recording time.

## Explicit interruption cleanup

File protocol version 2 adds operation 7, with exact `DELETE INTERRUPTED` confirmation. Main accepts normal library version 1 for existing functions but refuses operation 7 without version 2 support. Both account roles use the same authenticated, origin and CSRF protected endpoint. Incident and alert readiness checks apply before queueing and offering the request. The camera checks new protection/recovery work before every worker step.

The recorder first scans verified metadata, deleting only recovered clips older than the operation cutoff. Its associated private recovery files are removed before the public video, retaining a readable copy if cleanup is interrupted. Two bounded directory passes then clear recognized orphaned recovery archives and inactive role-matching recording fragments. A surviving public recording, the original active identity, the current active recording, unknown names and other-role files are excluded. Unknown or damaged records are not guessed to be interruptions. Completed deletions and recovery file removals are reported separately; a failed operation can have a partial result. Work retains the existing 90 second camera, 120 second Main and 125 second browser deadlines. No cleanup intent or recording pause is persisted.

The normal communication path is unchanged: one paced camera HTTP owner, one second command polls and five second ordinary heartbeats, with role staggering, early state-change reports, shared error cooldown and incident ACK priority. Main holds one five-entry result per camera and never buffers video. Closed browser lists issue no SD page requests; opened lists refresh on changed saved-record counters or their existing periodic interval. The cleanup phase and its directory scans run only for an explicit operation 7. Host simulations check policy, bounded requests and retained allocations; physical SD unlink latency, frame continuity, RF conditions and runtime heap still require the hardware acceptance run.

When both dashboards ask for the same camera page while it is being read, Main shares the in-flight request instead of starting another SD scan. Completed replies retain one bounded page per camera; each HTTP response consumes a temporary copy rather than clearing the shared page. Expired results are released during request or camera poll handling after the existing 120 second request window. Native allocation checks cover two maximum five-entry pages, repeat reads and a failed response allocation without losing the retained result. These are host allocation observations, not measured ESP32 runtime heap.
