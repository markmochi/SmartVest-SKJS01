# Dashboard responsiveness

Main uses bounded transport, scoped responses and prioritized browser reads to address delayed loading while a phone remains associated with the vest. Install Main with the supplied partitions and erase-all disabled. Product version remains 1.0. Installed-device acceptance must be recorded after this build is flashed.

## Transport

Main completes the three-second white LED sequence and saved-state initialization before exposing its Wi-Fi network. It initializes TCP/IP, installs dashboard and connectivity-check routes, checks that HTTP is listening, and creates the dashboard task. That task then starts Wi-Fi and services DNS and HTTP. A failed listener or task allocation does not advertise an unusable hotspot. Early network initialization failures retry at five-second intervals without repeated event subscriptions. Captive routes are registered from the configured mode, including when DNS needs a later bind retry. Actual first-connection behavior and device network-selection policies still require physical verification.

The pinned ESP32 server defaults to TCP Nagle buffering. Main now enables TCP_NODELAY on accepted sockets. The cooperative writer joins the header/body boundary into one packet of at most 1,460 bytes, without allocating another complete response. Exact partial writes, independent socket slots, request/response caps, absolute deadlines, camera signatures and explicit buffer release remain enforced.

Flash-backed HTML and asset transfers allow up to 30 seconds in total and four seconds without progress. Ordinary responses retain their five-second total and two-second idle limits. This permits a slow but progressing page download without enlarging the four socket slots, response RAM cap or internal-heap reserve. A genuinely stalled transfer is still closed.

The unchanged full JSON route is retained for compatibility and explicit diagnostic downloads. Ordinary administrator pages continue to select their existing status views. Rider pages use `rider/status?view=overview`, `equipment`, or `activity`, so Overview no longer repeatedly serializes camera help, cellular details and all alert history. Default `rider/status` remains the full response; unknown views return 400. Rider response allocation is bounded and appears in administrator HTTP response metrics under `rider`. Rider location indicators read compact GPS telemetry and the current HDOP condition directly, without allocating a full diagnostic GPS JSON tree. The freshness and HDOP threshold remain the same; HDOP is not treated as measured error in metres.

Ride Test uses `status?view=ride`. It retains every module section the recorder actually saves, while excluding unused incident histories, recent SMS, HTTP/radio diagnostics and console details. This does not remove fields from saved module observations. Full diagnostics remain explicitly available; exports can still expose a genuine allocation failure under insufficient memory.

The Cameras page first reads `cameras/monitor?view=summary` and displays the two current camera reports. It then requests at most one eight-event history page per polling cycle with `view=events`, which omits camera telemetry. History runs as a single independent follow-up: a stalled event request does not delay scheduling the next live-status read. History failures retain current camera cards and produce a local history message with a six-second retry delay. The initial page displays both camera cards before its first response. Navigation or visibility cancellation stops the owned request; a late history response cannot overwrite another page. Full diagnostic downloads retain the original combined endpoint and cursor validation. Leaving the camera or modem page cancels its download reads immediately.

## Browser scheduling and recovery

The first HTML response contains the styles and small startup supervisor, authorized by exact generated CSP hashes. Login therefore keeps its appearance if a later script download fails. One shared runtime bundle and separate shared records and position bundles replace the earlier burst of independent module downloads. Saved modules are reused across page changes, and every retry refers to the same initialized session and request queue.

Startup and page modules recover automatically after failed or interrupted downloads. Each attempt has a 35-second deadline and bounded backoff; a fresh validated asset namespace avoids the browser's cached failed module graph. The 15-second connection message is informational and does not stop loading. Late older startup entries cannot initialize again, and obsolete page loads cannot replace the current page. Initial session, contacts and account GETs also retry temporary failures while retaining the page structure. Controls that require saved settings remain disabled until those settings arrive. Message, incident and rider activity pages render their sections before records arrive. Contacts and rider Account keep battery updates through the compact overview response instead of requesting all history. POSTs are never automatically repeated.

Navigation within the signed-in dashboard reuses its document, session and loaded modules. Changing pages cancels the previous page's reads and disposes its polling/scene before mounting the destination. Back/Forward navigation follows the same lifecycle. Sensing command confirmations and piezo listeners also belong to their mount; old work cannot update a newly opened Sensing page. Unsaved edits and an active Ride Test require a leave-page choice; submitted writes are allowed to finish. Contact and account saves protect navigation during the write; after a contact save finishes, a delayed verification read can be cancelled by leaving the page. Direct links and refresh still work through the original server routes.

The Sensing page uses one combined IMU/rider-pose response on a 350 ms target cadence, rather than independent full-IMU and 100-ms pose requests. The scheduler subtracts request time and keeps at least 50 ms between completed reads, without overlapping or catch-up bursts. The pose comes from Main's existing authoritative rider serializer, preserving readiness, calibration and freshness checks. Display smoothing remains local to the browser. Ride Test previews at up to four IMU observations per second and backs off on failures; diagnostic catch-up is bounded. These browser rates do not change 200 Hz acquisition/detection.

One API request remains in flight per tab. Explicit writes take priority over queued reads; foreground data takes priority over the background pose preview. A higher-priority request may cancel an in-flight GET. An in-flight write is never cancelled by this scheduler or automatically repeated. Obsolete queued reads cancel immediately, and session generation checks reject stale queued work.

GETs normally have a 4.5-second timeout; pose keeps its 1.5-second limit. Explicit longer read timeouts remain possible. Writes retain their existing 12-second timeout. Polling retries the first two transient HTTP 503 responses after 250/500 ms, then returns to bounded backoff. Errors remain visible and last readings retain their age. A successful response, not Wi-Fi association alone, establishes current data availability.

Main checks available internal byte-addressable heap before growing request bodies, diagnostic JSON documents, encoded responses and queued strings. These checks retain a 12 KiB network reserve and require a large enough contiguous block. Low-memory requests receive the existing bounded 503 response instead of taking the last available network memory. This is a resource guard, not a guarantee of worst-case driver allocation success.

Page and asset routes share one flash-table lookup instead of 48 additional per-route handler objects and path copies. The generated table stores the version prefix and MIME strings once, with compact bounded descriptors. URLs, exact version matching, gzip bytes, GET/HEAD behavior, canonical-host checks and unknown-route fallthrough remain covered by the production route fixture. This reduces startup heap use and keeps the new firmware inside its existing flash reserve.

The rider battery/freshness events also recognize scoped status URLs. Current readiness, stale-data rules, sensor health, session expiry, calibration acknowledgements and unsaved edits remain authoritative. The WebGL renderer retains display-rate smoothing without adding extra polls or GPU allocations.

Background reads keep Refresh visually steady on both rider and developer dashboards. Only a user-requested refresh disables the button until completion; requests still do not overlap. The developer Sensing view patches diagnostic nodes in place and resizes chart backing buffers only when their dimensions change. These changes retain expanded details, text selection and the existing visualization freshness rules.

Main shares the camera-summary and modem-trace entry serializers between their existing response paths to retain flash space for the Main battery estimate. Fields, freshness rules, owned string copies, paging and response memory guards remain unchanged.

## Verification and limits

See [Verification](VERIFICATION.md) for retained software outcomes, compiled Main inputs/image hash and flash reserve, and the [physical acceptance protocol](HARDWARE_ACCEPTANCE.md) for device trials. Host regressions execute the production transport, installed-core String methods and actual status/service writers. Browser regressions include two clients with delayed local GETs, a held pose request, transient 503 recovery, and genuine negative monitoring state.

Fixture timings and 32-bit allocation measurements are not physical Wi-Fi or ESP32 heap measurements. The complete post-flash acceptance workload is at least 65 minutes with both cameras and two dashboard clients. Include page changes, rider and administrator views, Ride Test, and expiry/relogin. Require no recurring 503, persistent loading placeholder, AP loss or reset. Retain the 9600-baud `[MEM]` and `[HTTP MEMORY]` lines, HTTP per-endpoint allocation counters, free/minimum/largest heap, camera freshness and reset reason if a stall recurs.

Rider sign-in snapshots only credentials instead of duplicating contacts and SMS histories. The normal saved password is derived once; the legacy factory alias remains verified, and private credentials, iteration count, throttling and factory-alias policy are unchanged. Administrator credentials are stored separately and use the same password derivation.


Administrator Account polls its compact account status; rider Account and Contacts retain compact status reads. Untouched Contacts forms reload saved details when the settings revision changes in another tab; unsaved edits are preserved and normal revision checks prevent overwriting newer saved data. Reset does not reload the whole administrator dashboard. Camera event history is collapsed initially; automatic updates change its contents without resetting the open state or selected filters. The rolling-buffer explanation has been removed from the Camera page.

Large `DeviceState` value operations are shared rather than duplicated at every transaction call site. They retain default C++ value semantics and do not add a retained heap cache or enlarge transport buffers.

Related administrator views, sensor tools, account/contact forms and Ride Test tools use shared cached bundles. Record and position bundles stay separate, so the administrator overview still does not load the live position scene. Compatibility module paths remain available, and identical re-export payloads share flash storage.

Hidden tabs pause polling and connection-age assessment. Returning to a tab starts an immediate read with a bounded seven-second reconnect grace period; writes remain disabled until a fresh reply. Actual readings keep their original age, and sustained loss still shows a reconnect notice. Brief server failures after a valid update retry without immediately replacing the view with a warning. Display failures and genuine stale status remain visible. Initial page connections use a quiet header status and recover automatically.

Rider setup uses short opacity/transform transitions, no animation library or looping welcome animation, and respects reduced-motion preferences. Its scene and polling are disposed when a step or session ends. Settings/forms and records share a cached bundle; rider views share the position bundle. The administrator overview still does not load the scene. Inline CSS is minified with the pinned esbuild dependency and its exact CSP hash is regenerated.

The welcome/contact steps load without the 3D scene; the optional position step requests it on demand and keeps Continue available during loading. Administrator overview and Ride Test share a cached console bundle, while sensor/scene code remains separate. Login and session responses share one serializer without changing password checks, cookies or session duration.
